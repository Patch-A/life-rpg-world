# 人生 RPG 首版投稿实施方案

日期：2026-10-11。状态：范围与实施建议已形成，应用尚未按本方案实现或验收。

## 1. 本轮目标与证据边界

用户已明确：尽快形成可提交、可体验的参赛版本，通过投稿与许愿池关联寻找反馈，再据反馈决定优化方向；持续在 GitHub 保存源码。用户已确认拥有 DeepSeek API Key，但余额、运行环境配置、真实调用及可用模型尚未验收。

当前开发基线：仓库 `Patch-A/life-rpg-world`，main 提交 `30c6070e63bf9c5c1aaf294faf96e896ee394aec`，应用根为 `site/`，线上为已有 Sites 第11版。保留当前星球、2D角色、目标、行动、记录、人生纪念及既有存档兼容规则。

本轮核实：Sites 项目当前为 custom 访问范围，外部受邀访客数为0。因此“有线上链接”尚不能证明评委或普通用户能体验。当前源码未具备真实模型驱动的目标拆解与结构化复盘闭环。

官方细则允许网站等形态及 URL 或 ZIP 投稿，要求作品可运行、可交互并展示 AI 价值；没有核实到必须先完成支付宝小程序上架的统一要求。官网最新延长公告写明12月6日零点截止、12月7日至15日评审、12月底公布。按更保守的12月5日晚前完成投递安排，报名时再次核对实际字段和时间。

未确认：每件作品是否收到具体评审意见；“帮你实现”后的关联、审核、展示和用户分发流程；赛事是否提供体验用户或平台接口。点击公开首页“人生RPG”许愿条目后进入支付宝登录，未继续登录或提交。

## 2. 首版产品承诺

建议首批面向成年用户，聚焦一个场景：用户有学习、创作或个人项目目标，却不知道今天如何开始，或做过以后看不见积累。

首版一句话：把一个目标拆成今天做得动的小任务，记录真实行动，用成长星球看见积累，并由 AI 根据记录建议下一步。

完整流程：输入目标和当天可用时间 → AI给出少量候选任务 → 用户修改并确认一项 → 完成后记录 → 成长与存档更新 → AI引用已有记录做短复盘 → 用户确认下一步。

最先跑通的示例为“完成一篇文章”：用户每天有20分钟，AI按草稿、资料、段落等实际阶段给出动作，而不是每次都生成相同的‘坚持20分钟’。累计时间不等于作品完成；完成目标仍由用户依据自己设定的成功标准确认。

此范围是实施建议，不代表已经获得用户效果证据。5人试用能发现明显问题，不能证明市场需求或长期留存。

## 3. 冻结首版范围

| 必须交付 | 具体边界 | 完成判据 |
| --- | --- | --- |
| 真实AI拆解 | 输入目标、成功标准、当天时间、主要障碍；输出最多3个动作，每个有完成标准、预计耗时、理由 | 不同上下文产生相应不同建议；可编辑、拒绝、重新生成 |
| 用户确认与保存 | AI只生成草案；确认后调用现有规则保存目标/行动 | 重复点击不重复创建，刷新可恢复，与其他用户隔离 |
| 行动记录与成长 | 沿用现有按日期记录、撤销、确定性XP规则 | AI不判定现实中已完成，不直接加经验或发奖励 |
| 短复盘与下一步 | 用户主动触发；读取所选目标的少量近期记录，显示引用来源 | 无记录时不编造；只提一项调整，确认后才建立行动 |
| 快速体验 | 提供虚构样例，缩短首轮填写；生日与照片为后续可选信息 | 首次体验无需先填写完整生日或上传私人照片 |
| 反馈入口 | 页面内‘哪里卡住了/建议有无帮助/希望补什么’，可附自愿填写的说明 | 反馈持久化，维护者可查看；记录版本与步骤，不自动附整份存档 |
| 投稿包 | 可访问URL、操作说明、AI说明、16:9封面、已知限制、版本对应关系 | 另一账号可完整体验；素材、声明和实际功能一致 |

既有生日、纪念、照片、储蓄等功能保留并确保不损坏，本轮不扩展。优先从入口降低负担，而非为了做新流程重写整站。

首版不新增：真实支付宝账单/步数接入、支付与交易、排行榜和社交、完整人生自动规划、更多角色/3D美术、无人确认的自动执行、多智能体编排。首版不承诺医疗诊断、投资或心理治疗。敏感目标不套用普通成长任务建议。

支付宝小程序是后续渠道任务，不列为这次网页投稿的默认前置。若登录后的报名要求有额外约束，先修订本方案。‘支付宝举办的比赛’与‘产品已经接入支付宝’需分别表述。

## 4. 实施顺序与停止条件

### S0：证明能够运行和让别人进入

1. 在适当环境按交接文件启动现有源码，核对D1/R2及全部已应用迁移；保存已有存档回滚证据。应用根是 `site/`。
2. 在服务端受保护配置中设置 `DEEPSEEK_API_KEY`，使用独立模型适配模块调用官方对话API。模型名称运行时配置，以账号与官方当前文档为准。先用虚构目标验证连通、耗时、超时与错误处理。
3. 先邀请代表性测试用户，核对非站点所有者在电脑、手机及计划使用的浏览器中的访问路径。评审入口需可公开或按评审方式授权访问；不能只靠开发者已登录的截图。
4. 当前 Sites 身份依赖平台可信注入头。保留已有访问策略，先验证邀请方案及用户登录条件。若需要公开入口，先做无私人存档的介绍/虚构演示，并设计登录后独立保存与AI额度策略；不能把所有访客映射成同一生产用户。访问范围扩大在实施完访问隔离后作为发布步骤处理。
5. 如果代表性用户在当前站点无法访问，或必须有其不具备的账号，立即把部署/认证适配列为阻塞项，选择可达的独立Web入口。新部署必须实现可信认证，不能直接沿用可由公网客户端伪造的身份头。避免同时进行完整小程序重写。

停止条件：模型不可用、评审入口无法授权、存档隔离不成立时，不进入公开试用。模型连通和访客进入是先验收的两个门槛。

### S1：完成一条AI行动流程

建议变更位置（新增文件名在开发时可调整）：

| 工作 | 位置/责任 |
| --- | --- |
| 模型适配、提示与结构校验 | `site/lib/ai/`：DeepSeek请求、超时、输入最小化、输出验证 |
| 拆解/复盘服务端入口 | `site/app/api/agent/route.ts`：可信身份、当前用户数据、配额与限流 |
| 确认写入 | 复用 `site/app/api/game/route.ts` 和 `site/lib/game.ts` 的规则；增加必要的草案确认动作 |
| 最小存档扩展 | 可选成功标准、复盘记录、版本字段；旧存档缺省补齐，不清空任何既有记录 |
| 前端体验 | 现有首页/目标流程：上下文、候选任务卡、确认、复盘、下一步 |

草案必须有结构约束：标题、步骤、完成标准、预计分钟、关联目标和理由。服务端检查长度、目标归属与允许的动作；JSON格式正确不代表语义正确。用户输入及存档内容视为数据，不能据其中的指令改变系统权限。

确认用幂等请求标识和现有revision冲突机制；创建目标与任务若属于一次确认，采用原子写入，避免网络中断造成半份结果。复盘引用必须指向该用户实际记录；无证据的推测标明，用户可以拒绝。

### S2：补齐试用与运行边界

1. 反馈独立存储，不混入成长经验。数据库迁移只增量；维护者通过受保护的管理方式读取，禁止公开反馈列表。展示维护联系方式或明确的反馈回执。
2. AI默认只接收所选目标、当天约束和必要的近期文字记录；首次调用前说明会传给DeepSeek。生日、照片、账目及整份人生存档不自动发送。用户可手动记录而不启用AI。
3. 明确数据删除、存档导出、备份、维护责任和试用期支持方式。上线前把保留期限与反馈是否匿名写清楚；不能用‘测试版’替代这些安排。
4. 首批建议每用户每天10次AI请求，并设全站可配置硬上限、单次输入输出长度、超时、并发限制和关闭开关。这个数量是初始运营建议，不是需求或费用事实；按真实消耗再调。预算、余额和告警渠道在部署前落实。达到上限后保留手动流程，不将模板冒充AI结果。
5. 简化首次引导时，同时检查生日/成年礼/衣柜逻辑对缺少出生信息的处理。不要只隐藏必填框而留下服务端或后续页面错误。

### S3：冻结、投稿、收反馈

1. 完成下面的验收清单，先找5位目标用户独立体验。记录哪里卡住、任务是否采纳、建议是否可执行，而不只问‘喜不喜欢’。
2. 每轮可体验版本同步GitHub：源码、增量迁移、配置示例、部署说明、素材来源、变更记录、投稿材料；密钥、用户存档、照片、数据库及依赖不进入仓库。GitHub私有存档与向评委提供访问分开处理，无需为参赛默认公开源码。
3. 对冻结版本记录Git提交、Sites版本、部署URL与日期，可用标签如 `submission-v0.1`；评审期间保持此版本可体验。后续更新留清晰记录和可回退版本。
4. 按实际报名页提交作品，并保存提交成功回执。正式条款由用户确认；参赛标题/声明不能声称尚未完成的小程序或阿宝接入。
5. 登录许愿详情，核对完整需求、‘帮你实现’按钮的实际作用、必填项和展示路径，再关联已运行的作品；保存关联回执和用户可见入口。关联完成不等于已分发或已得到反馈。
6. 发布后3至7天回访首批用户。先修访问/保存/错误记录/AI不可用，再修任务不可执行，最后根据多位用户的重复反馈选择界面或扩展功能。没有反馈时先查访问和体验完成率，不能推断没有需求。

## 5. 投稿前必须通过的验收

- [ ] 非开发者账号能够进入，入口与授权说明一致；在真实手机及计划使用的支付宝内浏览器路径检查主流程。
- [ ] 从目标输入到AI拆解、修改确认、行动记录、复盘与下一步，全流程真实运行。
- [ ] 两个账号数据隔离；退出/拒绝授权后不暴露已有用户数据；虚构演示和个人存档分开。
- [ ] 刷新可恢复；重复确认不重复写；旧目标、照片引用、生日、纪念与领奖标记保留；有回滚方案。
- [ ] 断网、模型超时、额度不足、无记录、冲突、空输出与不合法输出都有可理解的恢复路径。
- [ ] AI不编造完成记录或证据、不直接改XP、不执行支付或读取未知支付宝能力。
- [ ] 密钥不出现在浏览器包、接口返回、日志或Git；运行配额和关闭开关有效。
- [ ] 反馈能提交、可由维护者读取，用户知道数据用途和删除方式。
- [ ] 素材和依赖来源可追溯；投稿说明列明DeepSeek及实际数据来源，演示数据明确标注。
- [ ] GitHub提交、线上版本、提交材料一致；提交成功回执可核对。

本轮仅做方案、源码/平台配置阅读与官方来源核查，没有运行应用测试或完成上述验收。遵守仓库AGENTS：后续用户要求实现验证时，再运行现有脚本和必要的实际流程检查，并注明覆盖范围。

## 6. 最容易忽略的三个判断

1. “先提交再由评审告诉我问题”不是可靠的唯一反馈渠道。已核验细则没有找到保证逐件给出具体诊断的条款；因此自主试用、页面反馈和维护者回访必须先建立。
2. “有API Key”不等于产品已经有可用AI。余额、受保护配置、运行环境出站连接、响应时间、费用上限和错误恢复都需要真实验证。
3. “完成投稿/点击帮你实现”不等于完成用户分发。需要确认用户能找到并进入、能完成第一项行动、能反馈，随后才能讨论优化效果。

## 7. 当前下一项工作

先完成S0的模型与非所有者访问验证，并落实首版预算；通过后按S1实现。时间安排以这些结果为依据，本方案不承诺未经运行验证的开发天数。用户当前无需继续挑选美术或扩展玩法；开发阶段需要用户在受保护配置界面填入密钥，以及在提交时核对本人资料和正式条款。
