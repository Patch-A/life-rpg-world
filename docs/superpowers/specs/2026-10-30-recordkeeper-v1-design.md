## 一、这是什么

**给一个已经做出来的 demo，补上它唯一缺的那一块。**

现有 `C:\Users\Patch\life-rpg-world\site` 是 Codex 做的人生RPG demo（React 19 + Next 16/vinext + Cloudflare D1 + DeepSeek），已经具备：目标、行动、记录（Log）、经验值、等级、人生纪念、生日、2D 角色与语音气泡、DeepSeek 行动建议与复盘、邀请码与私人存档。

**缺的不是功能，是人。** 那个会说话、记得你、能接住你的角色，一行都还没有。

记录官就是这一层：补在现有 demo 之上，不动已有的骨骼。

**一句话：打开就看到一个人，跟他说今天，聊完东西就记下了。**

> 2026-10-30 本人纠正：这不是重做一版游戏，现有 demo 的工程不必推翻。要加的是"跟人聊天"这件事本身。

## 二、为什么要做

V1 被判死刑的三条原话（2026-10-29 访谈）：

> 「太卡片式了，整体布局很有 AI 味。它不像一个游戏，更像一个记录事情或学习计划的工作台。」
> 「如果是作为一个游戏，然后去让用户去玩或者去用的话，可能连我自己都不是很愿意去玩。」
> 「我最重点的是呈现方式，要是一种游戏形式。」

而下班后最想做的事是：

> 「通过模拟 AI 交互来记录……核心是交互过程。」
> 「我可能看到一个画面，只是一个人，他在跟我说话。」

**V1 缺的不是功能，是"人"。** 卡片再多也不会说话，表单再短也不会记得你。

## 三、目标 / 非目标 / 反目标

### 目标（V1 要达到）

1. 打开首页，第一眼是"有人在"，不是一屏卡片
2. 说一句话，助手接住、追问、给反馈
3. 聊完，今天说过的东西自动变成可看的记录，不需要你再填一遍
4. 能导出 MD，拖进 Obsidian 就能读
5. 手机和上班摸鱼时的桌面都能打开

### 非目标（V1 明确不做）

- **重做现有 demo**：目标、行动、记录、经验值、人生纪念、角色、DeepSeek 建议与复盘，全部原样保留，不重构、不推翻
- 怪物、经验值、奖励转盘（奖励转盘指新增的抽奖形式；现有的经验值不动）
- 语音输入（STT）—— 先只做"它用声音回你"
- 房间随季节/节点变化（只留数据结构位置）
- 自动写入 Obsidian 文件系统（部署在 Cloudflare Worker，读不到本地磁盘；只能导出下载）
- 多人、社区、下棋、PK
- 接支付宝身份、账单、步数

### 反目标（做出来也算失败）

- 做出来还是"卡片 + 表单"，只是换了个皮
- 助手说教、给 KPI、在你最累的时候布置作业
- 每次从零开始，不记得你说过什么
- 聊天记录变成第二个需要维护的列表

## 四、已经定下的规则（本人拍的，不可改）

这七条是 2026-10-29 / 10-30 两轮对话中本人明确确认的。实现时违反任何一条即为偏离。

### 4.1 助手是同一个人，两种姿态

- **陪伴者**：在场、接住、给台阶
- **咨询师**：引导、拆解、给方向
- 同一个形象、同一份记忆、同一个声音，只是姿态不同

### 4.2 切换边界

判断依据是**你说的话要不要"一个东西"**：

| 你说的话 | 姿态 |
|---|---|
| 明确的动作请求（"帮我算下这个月还剩多少"） | 咨询师 |
| 明确的情感表达（"今天好累"） | 陪伴者 |
| 含糊、两者都有 | **默认陪伴者** |

默认偏向陪伴者，因为**误判代价不对称**：猜错成陪伴者，最坏多问一句；猜错成咨询师，就是在低落时给人布置作业。

**升级要问，降级不用**：陪伴者 → 咨询师必须先问一句"要不要我们现在理一下"；咨询师 → 陪伴者可以自动。

### 4.3 记忆是地基，不是加分项

"咨询师"和"越用越懂我"是绑死的。每次从零开始问，那就只是客服。

### 4.4 怪是处境，不是对手（V1 不实现，规则先写死）

- 怪的强弱由**处境**决定（比如真被裁了，那只怪就该更重），不由**今天的产出**决定
- 情绪变好和干活一样能打怪
- 什么都没做但还在撑，不该长得更凶
- 三件事全崩的晚上：不审判，给台阶 + 主动开正向话题

**这条现在不实现，写在这里是为了防止以后做歪成"又一个 KPI"。**

## 五、V1 的循环

```
打开首页
  → 助手在那儿，有一句开场（模板，不耗额度）
  → 你打一句话（或点它给的快捷回复）
  → 它回你（文字 + 可选语音朗读）
  → 它从你的话里抽出 1-3 条记录，显示「我记下了这些」
  → 每条记录旁边问一句「这算一次行动吗？」
      [算，记进 XX 领域 +30]   [就记着，不算]
  → 点「算」才转成正式行动，写进 Log、涨经验、进进度条
  → 今天的记录落在下方
  → 一个导出按钮 → MD 文件下载
```

**「记完可认领成行动」是本人 2026-10-30 拍定的。** 理由：如果聊天记下的东西只进记录、不碰经验值，它就成了又一个需要维护的列表，正好撞上反目标。但也不许自动涨分——必须你点头，否则随口一句也算行动，经验值就废了。

**V1 只走这一条路。** 怪物、升级、房间变化全在这条路之外。

## 六、怎么落地

### 6.1 数据库：不改

`saves.data` 存的是整份 `Game` 的 JSON。新字段加在 `Game` 类型和 `normalizeGame` 的默认值里即可，**不需要 Drizzle 迁移**。

`agent_runs` 表直接复用：`mode='chat'` 存在 result 的 JSON 里，`goal_id` 存 `''`。每人每日 10 次不够聊天用，chat 走**独立额度**（见 6.8）。

### 6.2 数据模型新增

```ts
// 一条记录（你说的话被整理成的样子）
type JournalEntry = {
  id: string;
  date: string;          // YYYY-MM-DD，北京时间
  at: string;            // ISO
  text: string;          // 你的原话（保留原貌，截断到 400 字）
  summary: string;       // 助手压缩的一句话
  domain?: Domain;       // 识别不出就不填，不硬塞
  tags: string[];
  posture: 'companion' | 'counselor';
  runId: string;         // 对应 agent_runs
  status: 'pending' | 'claimed' | 'kept';  // 待认领 / 已转行动 / 只留着
  logId?: string;        // 认领后指向生成的 Log，用于撤销
};

// 一轮对话
type ChatTurn = {
  id: string;
  date: string;
  at: string;
  role: 'user' | 'assistant';
  text: string;
  posture?: 'companion' | 'counselor';
};

// 长期记忆：关于你的事实
type MemoryFact = {
  id: string;
  text: string;
  kind: 'fact' | 'preference' | 'situation';
  firstSeen: string;
  lastSeen: string;
  weight: number;        // 被提及次数，用于淘汰
};

// 怪物占位（V1 恒为空数组）
type Monster = {
  id: string;
  name: string;
  kind: 'life' | 'setback' | 'emotion' | 'jobless';
  hp: number;
  maxHp: number;
  createdAt: string;
};

// Game 新增三个字段
type Game = {
  // ...现有字段不变
  journal: JournalEntry[];
  chat: ChatTurn[];      // 只保留最近 60 轮
  memory: MemoryFact[];  // 上限 40 条
  monsters: Monster[];   // V1 恒为 []
};
```

`normalizeGame` 给三者补默认空数组，旧存档无需处理。

### 6.3 记忆怎么来

**蒸馏不单独调用模型。** 记忆候选随主回复一起返回（契约里的 `memoryCandidates`），一次调用同时产出「回什么话」和「记住什么」。

理由：独立蒸馏会让单条消息的延迟和成本翻倍，而聊天额度本来就要跟它共用。一次调用、两样产出，是最省的路径。

- 上限 40 条，超出按 `weight` 低 + `lastSeen` 旧淘汰
- 新候选与已有记忆相似则合并（`weight += 1`，更新 `lastSeen`），不新增
- **V1 不接向量库**。理由：记忆是"关于你的事实"，不是"文档检索"；强类型 + 上限比 RAG 更可控，而且部署在 Cloudflare Worker 上根本读不到本地 vault
- 蒸馏失败（模型没给或格式不对）→ 丢弃，主回复照常，不写半成品

### 6.4 后端

新增 `POST /api/chat`，复用 `/api/agent` 的原子预留机制，但**独立额度**（见 6.8）。

**助手能看到什么（本人 2026-10-30 拍定：全部）。** 请求里带上：

- 最近 20 轮对话
- 全部 `memory`
- `goals` 的标题、进度、目标值、单位
- 最近 20 条 `log`
- 今日 XP 与等级
- 储蓄类目标的当前净值

照片与文件内容**不发送**。因为要发这些，`/about` 页必须同步改，明说"聊天会把你的目标、记录与储蓄进度发送给模型"。

契约文件 `lib/ai/chat-contract.ts`：

```ts
{
  reply: string,                 // 助手说的话
  posture: 'companion' | 'counselor',
  askSwitch: boolean,            // 想切咨询师时必须为 true
  records: [{
    summary: string,
    text: string,                // 必须是用户原话的子串
    domain?: Domain,
    tags: string[]
  }],
  memoryCandidates: [{ text: string, kind: 'fact'|'preference'|'situation' }],
  quickReplies: [{
    label: string,               // 按钮上显示的字
    kind: 'say'|'accept-switch'  // 普通回复 / 同意切咨询师
  }]
}
```

服务端强校验（防模型跑偏）：

- **姿态升级必须用户点头。** 请求里带 `switchConsent: boolean`，前端只在用户点了 `kind: 'accept-switch'` 的按钮时才置 `true`。服务端校验：`posture === 'counselor' && 上一轮是 companion && !switchConsent` → **强制改回 companion**，并把 `askSwitch` 置为 `true`，让模型重新问一次。不靠对用户文本做启发式匹配
- 降级（咨询师 → 陪伴者）自动放行，服务端不拦
- `records[].text` 必须是用户本次原话的子串。不是就丢弃，**防止编造你说过的话**
- `records` 最多 3 条，`quickReplies` 最多 3 条
- 模型返回不合法 JSON → 本次不写入任何东西，返回友好错误
- **不流式**（V1）。沿用现有 `stream:false` + `response_format:json_object`：结构化的 `posture` / `records` 必须整体校验通过才能落库，流式会把这件事变复杂。等待期间前端显示"正在想…"并禁用发送

### 6.7 写入路径（回答"谁写存档、并发怎么办"）

**只有一条写路径：`POST /api/game` + `reduceGame`。** 不新增旁路写入，否则会跟现有的 revision 乐观锁打架。

流程：

1. 前端 `POST /api/chat`，只拿契约结果，**不写任何东西**
2. 拿到结果后，前端立即用现有 `mutate` 调 `POST /api/game`，action 为 `chat-turn`，把这一轮的用户话、助手回复、抽出的记录、记忆候选**一次性写进存档**
3. `/api/game` 照旧走 revision 校验；冲突就走现有的 `setConflict(true)` 提示，输入保留

**未确认的记录立刻落库。** "我记下了这些"在用户确认之前就已经是 `journal` 里的一条，状态为 `pending`。刷新后还在，不会丢。点「算」→ 状态变 `claimed` 并生成 Log；点「不算」→ 状态变 `kept`，只是留着。删除即删除。

理由：如果等确认才写，用户关掉页面就丢了；如果写在 `/api/chat` 里，就要自己再造一套锁。

`reduceGame` 新增三个 action：`chat-turn`、`claim-record`、`delete-journal`。

### 6.8 额度

| 项 | 值 |
|---|---|
| `AI_CHAT_USER_DAILY_LIMIT` | 50（本人 2026-10-30 拍定） |
| `AI_CHAT_SITE_DAILY_LIMIT` | 500 |
| 计数表 | 复用 `agent_runs`，`mode='chat'` |
| 与 `/api/agent` | **分开计数**，互不占用（`agent_runs` 按 `mode` 过滤后各自计数） |
| 原子预留 | 沿用（含 90 秒 pending 锁，防连点） |

注意：90 秒 pending 锁意味着**上一条还没回完时不能发第二条**。聊天场景下这是可接受的（本来也是一问一答），前端要在等待时禁用发送按钮并显示"正在想…"。

额度用尽：返回友好文案 + 保留手动记录入口（现有表单原样可用）。

### 6.9 跨天与开场

- **开场白是模板，不调模型。** 否则每次打开都花一次额度、等 5-10 秒，模型挂了就直接违反首要目标（"打开就看到一个人"）。
- 模板按时段选（早/午/晚/深夜），可插入当天已有记录数
- `chat` 保留最近 60 轮，跨天不重置；每天第一条前插一条系统分隔（不消耗轮次预算）
- 模型不可用时：助手仍在场，说一句模板话 + 提示"今天它有点累，可以先用表单记录"

### 6.10 首页布局取舍

现有 `ActionAssistant`（DeepSeek 拆解/复盘）与新的对话都是 AI 入口，同屏会互相稀释。

**决定：`ActionAssistant` 移到"行动"页，从"今天"页移除。** 它本来就是面向单个 Goal 的，放到 today 反而不对。

### 6.11 记录与记忆的可见性

- `journal`：每天可见，可删单条，上限 500 条（超出删最旧，并提示"已归档至导出"）
- `memory`：设置页新增"它是怎么记住我的"一页，列出全部事实，可单条删除，可整体清空
- 两者都不进 Wiki、不外发；导出只含当天 journal，不含 memory

### 6.12 开源与自带模型（本人 2026-10-30 追加）

项目要开源，下载的人填自己的 key、用自己的模型。

**做部署者级，不做用户级。** 一个人部署、一个 key，配在环境变量里。多用户各自填 key 需要加密存储、轮换、泄露处置，V1 不碰。

**必须真的能换模型。** 现在代码有三处 DeepSeek 专属写法，换到 OpenAI / Ollama / vLLM 会 400：

| 写死的 | 改成 |
|---|---|
| `https://api.deepseek.com/chat/completions` | `AI_BASE_URL`（默认 `https://api.deepseek.com`）+ `/chat/completions` |
| `thinking:{type:'disabled'}` | 只在 base URL 含 `deepseek` 时发送 |
| `response_format:{type:'json_object'}` | 先带；若返回 400 提到 response_format，去掉重试一次 |

**配置回落链**（保证现有部署不改也能跑）：`AI_API_KEY ?? DEEPSEEK_API_KEY`、`AI_MODEL ?? DEEPSEEK_MODEL`。

**没配 key 时**：聊天入口在，助手说一句「还没配置模型」，手动记录照常可用——不能白屏、不能崩。

**JSON 解析要宽容**：有的本地模型会在 JSON 外面包 ```json 围栏。解析前先剥围栏。

**密钥安全**：只读环境变量，不回传前端、不写日志、不进错误信息。

**交付物**：`.env.example` + README 的自托管一节，写清楚三步：填 key、改 base URL（非 DeepSeek 才需要）、`npm run dev`。

### 6.13 同意与隐私（本人 2026-10-30 拍定：沿用现有规则）

不新增门槛，但要做两件事：

1. **沿用**现有的 18+ 门槛和"同意发送哪些数据"勾选，不弹第二次。首屏不被打断——这是"打开就看到一个人"的前提
2. **`/about` 页必须更新**：现有文案承诺"不会自动发送生日、照片、其他目标或储蓄账目"，而聊天会发目标、记录和储蓄进度。不改就是虚假承诺
